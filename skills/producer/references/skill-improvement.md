# 方法改进与项目隔离

实战反馈既可能暴露方法缺陷，也可能只是项目选择变化。先完成当前项目需要的修正，再决定是否改变通用能力。

## 找到问题所在

- 输入不足：补材料或说明，不把缺失事实编成方法。
- 项目决定或环境变化：更新该项目的简报、研究和约定。
- 执行失误：纠正执行，确认已有方法为何没有被使用；不通过堆规则掩盖未遵守原规则。
- 通用方法缺陷：指出现有方法无法解决的专业问题及证据，形成有边界的修改。

一个问题可以同时涉及多项原因。不要只因用户说“写得差”就把当前喜欢的文体写成全局要求；要定位内容、逻辑、语言或用途适配究竟哪里失效。

## 改进候选必须具备的内容

说明失败机制、采用的方法或专业依据、适用情境、不能采用的情境，以及如何观察它是否有效。方法可以针对一种真实文体或工艺，不必适用于所有领域；但要由专业对象和机制定义条件，而不是把某个项目换个名字。

优先补诊断、操作和验证能力。单纯增加“更高级”“更自然”“必须优秀”的目标，或列一串学科和权威链接，都没有教会 Skill 改善结果。

## 验证与更新

保留原失败输入和改前产物，使用修改后的方法完成实际任务，再用不同用途的输入和不应采用该方法的反例检查。按影响范围验证，比较真实结果，不给自己未经定义的分数。结构校验只能发现结构问题，不能代替专业效果检验。

原始案例、客户反馈、项目研究和验证产物保留在所属项目或维护项目。底层 Skill 只获得必要的通用方法及独立通用示例。匿名化、参数化、改名、放进引用文件或添加条件句都不能使项目属性变成专业知识。

在授权范围内安装或分发已验证修改，保存可比较的版本与回退路径。未通过的修改留在维护项目，不作为已完成能力推广。改善一个项目不是改善所有用途的充分证据。
